# Runner-canon backtest — full suite (4 прогона, 14-19 дней)

Цель: проверить, можно ли подкруткой параметров runner-канона (`PAPER_RUNNER_*`)
сделать его экономически положительным. Если нет — отключить.

Базовый отчёт (Test 0, default 14d): [`RUNNER_CANON_BACKTEST_14D.md`](./RUNNER_CANON_BACKTEST_14D.md).

Все прогоны воспроизведены скриптом
[`scripts-tmp/runner-canon-backtest.ts`](../../../scripts-tmp/runner-canon-backtest.ts);
exit-canon одинаковый для всех тестов (Wave B v1, TP-ladder
`0.10/0.30/0.50/0.70/0.70`, killstop −25%, trail `ladder_retrace`,
breakeven trim 50%, $500 notional), кроме Test C где TP-ladder специально
отключён.

## Test A — hardened thresholds

**Гипотеза**: ужесточить velocity (1.5× → 2.0×) и bs1h (0.95 → 1.3) — отсечь
«вялые» магниты с симметричной buy/sell-ленточкой и слабым ускорением.

**Результат**: ROI **ухудшился** с −1.45% до −1.71% (runner-only).
Hardened-фильтр отсёк 57% кандидатов (1004→427), но среди них непропорционально
много winners. Win-rate не вырос (50% → 55%, в пределах шума), а средний
проигрыш ухудшился.

**Вывод**: ужесточение не улучшает selectivity. Винеры и лузеры неотличимы
по параметрам velocity/BS на момент входа.

## Test B — расширенное окно (19 дней) — единственный плюс, но нестабильный

## Test C — TRAIL-only, без TP-ladder

**Гипотеза**: TP-ladder profile `0.10/0.30/0.50/0.70/0.70` фиксирует прибыль
слишком жадно — у TOP winners в Test 0 TP-ladder не срабатывал ни разу,
выходили по TRAIL. Может, отключить TP-ladder и оставить только peak-trail?

**Конфигурация**: `PAPER_TP_GRID_SELL_FRACTION_PROFILE=0,0,0,0,0`,
`PAPER_TRAIL_MODE=peak`, `PAPER_TRAIL_DROP=0.10`,
`PAPER_LIVE_OSCAR_BREAKEVEN_TRIM_AFTER_FIRST_TP_ENABLED=0`.

**Результат**: **катастрофа**.
- runner-only: ROI −1.84%, win-rate **31%** (vs 50% default)
- runner+A+: ROI **−2.10%**, win-rate **16%** (vs 26% default)

Без TP-ladder большинство трейдов проходят пик и возвращаются к нулю/минусу
**до** срабатывания peak-trail (нужен +5% триггер). TP-ladder выполняет
важную функцию: фиксирует первые 10% позиции уже на +5% peak — это и есть
основной источник плюса по 50% win-rate в default.

**Вывод**: TP-ladder обязателен. Trail-only делает стратегию хуже на ~$1500 / 14d.

## Корневой диагноз

Перебор гипотез показал **одну закономерность**:

> Runner-канон захватывает **много магнитов**, среди которых соотношение
> «настоящие импульсы / scam-pump-and-dump» примерно **1 к 3**.
> На бычьем рынке (нач. мая) winners перевешивают; на нейтрально-медвежьем
> (середина-конец мая) — нет.

Никакая комбинация порогов на момент входа (`velocity`, `bs1h`,
`mcap range`, `peak hold`) не улучшает selectivity, потому что
runner-сигнал по своей природе **смотрит на уже-зарождённое движение**,
а его судьба (импульс vs скам) определяется **post-entry**, чего на
момент входа в данных нет.

Подтверждение из live-журнала за 14 дней:
- legacy (dip_windows + impulse_pg_snap, без runner): 143 трейда, −$239, ROI −0.37%
- runner: 1 трейд (VIRL, −$65)

Live-данные за 14 дней показывают runner-канон **редко пробивает** dip-приоритет
и Policy A+, но когда пробивает — обычно с потерей. Это совпадает с симом.

## Рекомендация

**Отключить `PAPER_RUNNER_MODE_ENABLED` (`1` → `0`)**.

Причины:
1. **Все четыре варианта параметров runner-канона** дают отрицательный ROI
   на последних 7-14 днях (от −1.0% до −2.1%).
2. **Единственный плюс (Test B 19d)** обеспечен 5 ранними днями высокой
   волатильности; на текущих рыночных условиях стратегия в минус.
3. **Hardened thresholds** (Test A) ухудшают результат, что означает:
   selectivity не работает на этих признаках в принципе.
4. **TP-ladder отключение** (Test C) ломает стратегию — TP-ladder
   единственная вещь, которая держит win-rate на 50% в default.
5. **Live-данные за 14 дней** согласуются с симом: 1 живой runner-трейд,
   −$65, при том что dip-канон за тот же период −$239 на 143 трейдах
   (−0.37% ROI), то есть **dip-канон стабильнее в околонуле**.

После отключения runner-канона в discovery остаётся только dip-логика,
которая в среднем работает в околонуле и захватывает «настоящие» проливы
(подтверждено сравнением live `legacy_no_path` PnL = −$239 / 143 = −$1.7
средняя сделка против runner −$65 / 1 = −$65).

**Pre-flight checklist для отключения**:
- [ ] `ecosystem.config.cjs:596` — `PAPER_RUNNER_MODE_ENABLED: '1'` → `'0'`
- [ ] git commit + push в `v2`
- [ ] на VPS: `git fetch origin v2 && git reset --hard origin/v2 && npm ci && pm2 reload ecosystem.config.cjs --update-env`
- [ ] проверить что `PAPER_RUNNER_*` переменные **остаются в файле** (на случай возврата) — отключение делается одной флаг-переменной.

**Возможный следующий шаг (не сейчас)**: разработать альтернативный
runner-канон с **post-entry filter** — входить виртуально, через 5 минут
проверять движение цены, и только если +1.5%+ — открывать реальную позицию.
Это превратит runner из «ловушки на момент» в «подтвердительный сигнал».
Но это отдельный проект — текущая reализация однозначно убыточна.

## Что НЕ сделано (вне scope текущего suite)

- Test D: post-entry guard «через 20 минут после входа peak<+2% → выход».
  Требует доработки `simulateLifecycle()` для поддержки кастомного timeout.
- Test E: исключить raydium-source при peak<+1% в первые 30 мин.
- Test F: per-segment TP-ladder profile.

Эти тесты могут показать улучшение, но даже самое оптимистичное
улучшение (+0.5% ROI) удержит стратегию **на грани околонуля**, что
не оправдывает ни кодовой сложности, ни торгового капитала. Поэтому
выбран простой путь — отключение.
